# Первый запуск обучения

Здесь всё собирается в эксперимент. Корпус в `data/tiny_ru.txt` написан для этого проекта: это короткие объяснения и предложения о языке и математике. Он очень мал, поэтому результат — демонстрация механики, а не полезный чат-бот. Не оценивайте масштабные языковые способности по этой модели.

## Команды

```powershell
docker compose --profile lab build lab
docker compose run --rm lab python -m unittest discover -s labs -v
docker compose run --rm lab python -m labs.experiments train --steps 400
docker compose run --rm lab python -m labs.experiments generate --prompt "модель " --tokens 180
```

Первое скачивание CPU PyTorch занимает время и место на диске; повторный запуск использует образ. Чтение сайта не зависит от сборки лаборатории. Чтобы увидеть параметры команд: `docker compose run --rm lab python -m labs.experiments train --help`.

## Как устроены данные

Программа делит исходный текст по позиции: первые 90% — train, последние 10% — validation. Словарь строится по train. Из каждой части выбираются окна длиной T+1. Первые T символов окна — вход, последние T — сдвинутая цель. Ни одно окно не пересекает границу частей.

Это базовый демонстрационный split. Для небольшого корпуса validation шумна и может содержать иной стиль. Для настоящего проекта выделяйте целые документы, удаляйте дубликаты и оставляйте независимую test-часть. В лаборатории отдельного test-корпуса нет; не называйте её validation результатом итогового независимого теста.

## Что наблюдать

Лог содержит step, train loss и val loss. `runs/metrics.csv` хранит историю текущего запуска. `runs/checkpoint.pt` сохраняет веса, словарь, конфигурацию и число выполненных шагов; `runs/sample.txt` — результат последней генерации. Повторное обучение перезаписывает эти файлы: для сравнения копируйте их в отдельную папку перед следующим запуском.

Перед шагом 1 выводится исходная ошибка. После обучения она обычно снижается, но каждый отдельный лог не обязан быть лучше предыдущего. Случайный классификатор по V примерно равновероятным классам даёт ориентир ln V. Частотный baseline часто лучше равномерного, поэтому «ниже ln V» — слабый критерий.

## Честная проверка

1. Запустите короткое обучение: `train --steps 40`.
2. Убедитесь, что нет NaN и ошибки форм.
3. Выполните более длинный запуск на том же seed.
4. Сравните ошибку и характер текста, а не только отдельную удачную фразу.
5. Выполните тест `test_overfits_small_batch`: он проверяет, что исправный цикл может запомнить маленький пакет.

Лабораторный checkpoint служит генерации, а не точному продолжению прерванного обучения: состояние Adam и RNG в нём не хранится. Это сознательное упрощение; для полноценного resume добавьте эти состояния и тест непрерывности траектории.

## Эксперимент: ширина и контекст

### Пример реально выполненного запуска

При проверке проекта стандартная конфигурация дала 107 904 параметра и словарь из 38 токенов. После 400 шагов train loss снизилась с 3,6658 до 1,2435. Validation сначала улучшилась с 3,6633 до примерно 2,4786 на шаге 150, но к шагу 400 выросла до 2,6107. Это характерное начало переобучения на маленьком корпусе, а не свидетельство поломки механизма градиента. Конкретные результаты на другой платформе могут немного отличаться.

Сгенерированный текст содержит знакомые фрагменты, но остаётся искажённым: маленькая символьная модель на нескольких тысячах символов не становится полноценным собеседником. Для улучшения нужны более подходящий корпус и контролируемое масштабирование, а не только дополнительные шаги. Историю своего запуска смотрите в `runs/metrics.csv`; следующий train её перезапишет. Готовые веса и результаты примера не включены в GitHub: вы получите их собственным запуском.

Измените только один параметр:

```powershell
docker compose run --rm lab python -m labs.experiments train --steps 400 --dim 96 --heads 4
docker compose run --rm lab python -m labs.experiments train --steps 400 --context 32
```

Запишите время, число параметров, train/val loss. Сравнение по одинаковым шагам не равно сравнению по одинаковым FLOPs: более широкая модель делает больше работы. Для серьёзного вывода нужен контролируемый бюджет и несколько seed.

## Задача

В логах train=0,1, val=4,5. Что вы проверите до изменения архитектуры?

<details><summary>Ответ</summary>
<p>Словарь и кодирование validation, сдвиг целей, отсутствие обучения на validation, распределение данных, дубликаты и размер train. Затем рассмотрите переобучение. Малая train loss сама по себе не означает, что модель научилась обобщать.</p>
</details>

Критерий готовности: вы можете повторить эксперимент по сохранённым настройкам и объяснить, что именно его метрика доказывает.
